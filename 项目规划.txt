# WhaleDot：开源桌面智能伙伴

**产品功能大纲 v0.2｜Project Autopilot 增强版**  
状态：设计讨论稿  
目标平台：Windows + DeepSeek Harness  
默认自主模式：**授权范围内自主推进**

---

## 1. 产品定位

WhaleDot 是基于 DeepSeek Harness（DSH）的开源、常驻桌面的个人 Agent，通过 Coopanion 风格的鲸鱼女仆桌宠，为用户提供主动通知、个性化智能回复、即时操作和长期项目自主推进能力。

### 1.1 核心目标

让用户从“持续向 AI 下达具体指令”，转向“设定目标、划定权限、监督成果”。

完整工作循环：

**用户描述目标 → WhaleDot 建立持续任务 → 自主规划下一步 → DSH 执行 → 独立验收 → 更新记忆与进度 → 继续推进或请求用户决策。**

用户不需要持续打开聊天窗口。鲸鱼在必要时通过桌面气泡主动汇报，并提供可直接点击的智能操作选项。

### 1.2 设计原则

1. **目标驱动**：优先推动可验证的目标进展，而不是机械执行任务列表。
2. **授权内自治**：用户一次授权明确的范围后，常规操作允许连续执行，超出范围必须确认。
3. **证据驱动**：进度由文件、测试、实验和交付物等证据确定，不接受模型单方面宣称成功。
4. **最小干预**：正常任务自动运行，只有阻塞、重大决策或有价值的进展才主动打扰用户。
5. **本地优先**：记忆、配置、权限和项目状态尽量本地存储，模型调用不受单一供应商限制。
6. **保持轻量**：复用 DSH 的模型、工具、会话、沙箱和权限，不开发第二套 Harness。

## 2. 用户自主模式

WhaleDot 提供三种模式，支持按项目配置。

| 模式 | 行为 | 适用场景 |
|---|---|---|
| 建议模式 | 自动观察和规划，执行前等待用户决定 | 新项目、重要方向选择 |
| **授权范围内自主推进（默认）** | 自动执行已授权的工作，重要节点请求确认 | 日常开发、实验、研究 |
| 高度自主模式 | 在更广泛但明确的授权内持续推进 | 稳定、可回滚的工程任务 |

### 2.1 默认模式的实际含义

用户可以预先授权：

- 在指定项目目录内读取和分析文件。
- 创建任务计划、整理报告和保存工作状态。
- 修改明确允许范围内的代码文件。
- 运行经过许可的本地测试和评估。
- 针对测试失败执行有限次数的修复。
- 创建工作分支、提交本地检查点。
- 在无需重大决策的情况下执行下一阶段任务。

上述行为并非默认拥有全部系统权限。实际操作仍须符合 DSH 的沙箱、工具访问与审批策略。

必须请求用户决定的情况包括：扩大项目目标、修改受保护文件、引入新的外部服务、执行高风险命令、删除重要数据、向远程仓库推送或发布内容等。

用户可随时暂停、修改或撤回自己的授权。

## 3. P0：首版核心功能

### F01｜独立桌面宠物

以 Coopanion 风格的鲸鱼女仆为主要交互角色。

支持透明置顶窗口、拖动、缩放、自由活动、屏幕吸附、鼠标穿透、触摸互动、角色动画、系统托盘、隐藏与低资源模式。

支持用户导入角色包，避免默认发行包依赖授权尚不明确的第三方贴图。

### F02｜Agent 状态动画

鲸鱼根据 DSH 真实事件显示待机、思考、阅读、执行、等待授权、完成、失败和暂停等状态。

状态映射由结构化事件驱动，不能仅根据模型自然语言推断成功。

### F03｜主动通知

用户无需打开 DSH，即可收到任务完成、失败、异常、审批请求、阶段进展和重要决策提醒。

支持消息分级、聚合、去重、延后、通知历史、免打扰和频率限制。

普通进度不要求立即弹窗，可合并到阶段汇报中。

### F04｜个性化多选项智能回复

根据用户偏好、项目上下文、任务状态和可执行操作，生成 2–4 个建议。

功能包括：

- 自动使用用户习惯称呼和语言风格。
- 根据个人工作习惯排列选项。
- 同时支持智能回复和智能操作。
- 支持 Tab 切换、Enter 接受、编辑建议及自由输入。
- 对需授权的操作展示简短风险提示。
- 建议过期、任务状态改变时自动禁用相关操作。

智能建议的显示文字与实际执行意图分离，避免模型生成的一句话被直接当作高权限命令。

### F05｜桌面直接对话

用户可以点击鲸鱼或使用快捷键打开简洁的交互气泡。

支持输入任务、继续已有 DSH 会话、查看简短结果、选择下一步操作，以及在必要时打开完整工作台。

### F06｜可靠操作路由

每个智能操作绑定原始通知、会话、项目、任务版本和实际执行意图。

必须实现权限校验、重复点击保护、过期检查、任务状态检查、结果追踪及异常恢复。

### F19｜Project Autopilot 最小闭环（新增）

用户以自然语言输入长期目标后，WhaleDot 提取：

- 目标和预期成果。
- 允许操作的项目与资源。
- 验收标准。
- 自主范围。
- 停止条件。
- 是否需要定期推进。

用户确认目标及权限后，系统自动建立项目记录、分解初始任务并执行第一项可验证工作。

第一版至少能够连续完成三个具有前后依赖的任务阶段，而不需要用户每一步重新发指令。

### F20｜持久任务调度（新增）

实现事件触发、周期检查、队列、任务锁、重试、暂停、恢复和状态持久化。

调度系统不自行执行项目操作，只负责将经过许可的任务交给 DSH。

### F21｜独立验收与进度判断（新增）

自动检查每项工作的实际成果，包括测试结果、文件变更、实验指标和预期交付物。

验收结果必须分为：通过、失败、证据不足、不可评分或执行结果未知，不能把缺乏证据等同于成功。

### F22｜执行权限与安全边界（新增）

建立项目级权限范围、工具调用门禁、独立工作区保护、执行限制、审计与可恢复机制。

在授权范围内尽量减少重复确认，但任何智能回复、自动触发或后台任务均不能绕过 DSH 的实际安全策略。

## 4. P1：完整个人 Agent 功能

### F07｜长期记忆与个性化

持久保存经过筛选的个人偏好、项目决策、工作习惯和历史反馈，支持检索、修改、删除和过期处理。

### F08｜主动个人 Agent

根据任务事件、周期检查、授权文件变化和目标进展判断是否需要采取行动。

支持建议、执行与提醒之间的合理分流。

### F09｜持续目标管理

建立跨会话项目目标，支持优先级、子任务依赖、阶段检查点、阻塞记录、终止和恢复。

长期目标不是独立聊天记录，而是一组持续维护的结构化项目状态。

### F10｜主动性和智能建议优化

通过用户选择与明确反馈，优化通知频率、建议排序及语言风格。

采用规则优先、模型辅助判断的策略，防止每个系统事件都触发额外模型调用。

### F23｜多阶段自主推进（新增）

在首版闭环基础上实现：

- 长期目标持续调度。
- 每轮完成后自动选择下一项任务。
- 阻塞原因识别与替代路径建议。
- 工作阶段检查点。
- 多轮失败自动停止。
- 已完成任务的验证与恢复。
- 一段时间没有进展时自动请求用户决策。

## 6. Project Autopilot：任务调度详细设计

### 6.1 从提示词到项目任务

用户输入：

“持续改进这个项目的测试通过率。先分析失败原因，只做最小修复，完成后运行测试，不要大规模重构。”

系统生成一份结构化目标：

| 字段 | 示例 |
|---|---|
| 目标 | 提高测试完整通过率 |
| 项目 | 用户选定的工作目录 |
| 允许行为 | 分析、局部代码编辑、测试 |
| 禁止行为 | 大规模重构、未经授权的删除 |
| 验收 | 固定测试集无新增回归 |
| 执行策略 | 最小修改、先定位再修复 |
| 触发方式 | 当前任务结束后继续 |
| 停止条件 | 完成、权限不足、持续无进展或达到执行限制 |

首次启用前，用户需要确认这些范围；之后不要求重复确认同一范围内的日常步骤。

### 6.2 调度器的四类触发器

**事件触发：** DSH 任务完成、测试结果出现、文件状态变化、审批结果返回。

**时间触发：** 定时检查、周期研究、阶段性汇报、延后任务重新启动。

**依赖触发：** 当前任务通过验收后，自动激活其后继任务。

**用户触发：** 通过鲸鱼输入目标、点击智能操作或修改项目设置。

事件驱动优先于固定轮询。多条相似触发应合并，避免重复启动相同工作。

### 6.3 任务状态机

每个执行任务遵循明确状态：

`PENDING → READY → RUNNING → VERIFYING → SUCCEEDED`

允许以下异常分支：

- `WAITING_APPROVAL`：等待用户授权。
- `BLOCKED`：客观条件阻塞。
- `FAILED`：明确失败。
- `UNKNOWN`：执行结果不确定，禁止盲目重试。
- `PAUSED`：用户或系统暂停。
- `CANCELLED`：取消且完成必要清理。

每次状态变更保存时间、来源、原因和执行标识。

### 6.4 连续执行规则

一次自主推进分为：

1. 读取项目目标及最新状态。
2. 选择一个当前可执行的原子任务。
3. 检查权限、环境和依赖。
4. 调用 DSH 执行。
5. 收集结果及执行轨迹。
6. 运行独立验收。
7. 更新任务与项目状态。
8. 判断继续、修复、暂停或请求用户决策。

不允许仅因为模型输出“还可以继续做更多事情”就无限生成新任务。

### 6.5 并发策略

建议首版：

- 同一项目默认只有一个写入型任务。
- 无冲突的只读分析可以并行。
- 多个项目可以分别排队，但必须有总执行容量控制。
- 相同任务通过稳定的任务键与运行标识去重。
- 并发写入要求明确的文件、分支和资源隔离。

后续可支持可配置的多 Agent 并发，而不改变上述一致性约束。

### 6.6 暂停与恢复

系统应在关键阶段保存执行检查点。

恢复时先检查原工作是否已完成，而不是直接重复操作。对发生超时、进程中断或结果未知的工具调用，必须先核对外部状态，再决定是否重新执行。

电脑或 DSH Host 关闭时，本地任务停止运行。重启后检查错过的调度点，对重复或已经过时的触发进行合并，不积压执行大量历史任务。

初期不要求断电时也能持续运行；未来可通过外部常驻执行节点扩展。

## 7. 持续记忆与上下文管理

### 7.1 记忆分层

| 层级 | 保存什么 | 更新方式 |
|---|---|---|
| Personal Profile | 称呼、语言风格、交互偏好 | 明确设置或用户确认的学习结果 |
| Project Memory | 项目目标、约束、架构、重要决策 | 项目状态变化与确认 |
| Task State | 当前任务、依赖、执行状态、检查点 | 事务化更新 |
| Episodic Memory | 每次执行的事件摘要与轨迹索引 | 运行结束后写入 |
| Evidence Store | 测试报告、指标、提交版本和验收证据 | 实际工具与验收器写入 |

### 7.2 记忆可信度

每条长期记忆至少保存：

- 内容、所属项目或用户。
- 来源和时间。
- 明确事实、用户偏好、模型推断或外部资料的类型。
- 关联证据或会话。
- 是否仍有效。
- 版本与冲突关系。
- 隐私范围。

用户明确表达的长期偏好应优先于模型推断；推断不得在无确认的情况下升级为永久规则。

项目文件、网页内容和工具输出属于数据来源，不因写入记忆而获得执行指令的权限。

### 7.3 上下文恢复

恢复任务时只注入必要内容：

当前目标、授权边界、最近检查点、待处理任务、相关决策及证据索引。

完整执行轨迹由 DSH 或外部记录按需检索，不要每次把整个历史聊天塞入模型上下文。

### 7.4 记忆治理

支持用户查看、编辑、导出和删除记忆；敏感信息默认不进入长期记忆。允许禁用自动偏好学习。

项目结束时可以归档并压缩任务记忆，但必须保留可追溯的关键证据。

## 8. 独立验收与项目进度评估

### 8.1 区分三种完成

**执行完成**：工具确实结束。

**任务验收通过**：具体任务满足预设的测试或交付条件。

**目标产生进展**：任务结果确实有助于长期目标。

三者不能混为一谈。

例如，代码成功修改并运行了测试，并不能说明识别率提高。

### 8.2 验收机制

按任务选择相应证据：

| 任务类型 | 主要验收证据 |
|---|---|
| 代码修改 | 测试结果、代码差异、静态检查 |
| Bug 修复 | 原故障重现记录、修复后测试、回归测试 |
| 模型实验 | 固定数据版本、逐样本输出、完整分母、统计指标 |
| 文档写作 | 文件存在、章节完整性、引用和需求检查 |
| 研究调查 | 原始来源、证据链、结论与不确定性 |
| 自动化任务 | 外部状态确认、运行记录、幂等检查 |

模型评分可作为辅助，但不应替代可用的确定性检查。

### 8.3 自动继续的判定

下一轮自动执行必须满足：

- 上一项任务状态明确。
- 必要验收已完成。
- 没有触发不可接受的回归。
- 仍处于目标与授权范围。
- 有新的、可验证的下一步。
- 尚未达到预算、尝试次数或停滞限制。

如果任务完成但没有进展，可以尝试有限次数的替代方案；持续没有改善则应停止并汇报。

### 8.4 防止项目发散

设置专门的 **Scope Guard（范围守卫）**：

- 禁止未经同意的架构全面重写。
- 限制单次任务的文件与模块修改范围。
- 不允许通过删除测试、改变验收分母或降低标准伪造提升。
- 不允许自动将实验目标替换成更容易完成的新目标。
- 对大规模依赖更新、新增框架和架构迁移要求确认。
- 保存失败实验和负提升证据，禁止只汇报成功结果。

建议把“变更规模”“回归数量”“有效进展次数”和“无效重复次数”作为重要监督指标。

## 9. 安全与权限边界

### 9.1 项目级权限

用户的授权应明确绑定项目，而不是对整个计算机永久生效。

建议权限等级：

| 权限类别 | 默认策略 |
|---|---|
| 已授权目录内只读分析 | 自动允许 |
| 读取允许访问的任务记录 | 自动允许 |
| 创建项目内非破坏性报告 | 自动允许 |
| 在隔离分支中局部修改代码 | 项目授权后允许 |
| 执行本地测试 | 仅在对应沙箱和命令策略允许时执行 |
| 修改项目范围外的文件 | 请求确认 |
| 删除重要文件、清理数据库 | 请求明确确认 |
| 安装软件、改变系统配置 | 请求确认 |
| 网络上传、远程推送、公开发布 | 请求明确确认 |
| 读取或传输凭据 | 默认拒绝，按必要的专门凭据机制处理 |
| 扩大长期目标和权限范围 | 用户直接确认 |

插件策略只会进一步收紧访问，不能覆盖 DSH 原生安全策略中的拒绝结果。

### 9.2 推荐默认限制

以下为建议初始配置，而非硬编码上限：

- 同项目写任务并发：1。
- 同一失败任务自动修复：最多 2 轮。
- 连续无实际进展：最多 3 轮后暂停。
- 自动操作限于授权的项目范围。
- 自动执行预算与时间上限：用户可配置。
- 高风险操作：必须明确确认。
- 未知执行结果：先核对，禁止直接重复执行。

允许用户对稳定项目提升运行预算和并行能力，但不允许通过调大预算取消危险操作的权限检查。

### 9.3 文件与结果保护

编程任务优先使用独立 Git 分支或 worktree。对无法使用 Git 的项目，采用适当的快照或备份机制。

自动修改之前保存可恢复状态，尽可能避免覆盖用户未提交的工作。回滚前要检查文件是否发生新的用户修改，不能直接覆盖较新的内容。

### 9.4 安全暂停

当出现下列情况时，Autopilot 必须停止后续高风险执行：

- 权限不足或授权撤回。
- 目标与现有约束冲突。
- 工作区或重要文件版本发生意外变化。
- 测试持续回归。
- 关键执行结果未知。
- 持续无进展。
- 无法恢复的工具错误。
- 用户主动暂停。

暂停应当保持所有已知证据，并说明如何恢复。

### 9.5 外部内容和提示注入

网页、仓库 README、日志、工具输出都可能包含不可信指令。它们只能作为任务数据，不能提升权限、修改授权或自行创建新的长期目标。

审批界面必须显示真实待执行动作与目标资源，不能只展示模型生成的友好描述。

## 10. WhaleDot 主动交互设计

### 10.1 三种通知

**进展通知**：有真实的新成果，告知用户关键变化。

**决策通知**：必须由用户确定下一步方向或授权。

**阻塞通知**：说明无法继续的原因、已有证据和可能的解决方式。

### 10.2 多选项决策

示例：

“小鲸发现修复后通过率没有提升，还出现了两个新回归。要怎么处理？”

智能选项：

1. “先定位新增回归，不继续修改。”
2. “恢复上次可用版本，保留实验记录。”
3. “让我看看这两次的完整差异。”
4. “暂停这个目标，晚点处理。”

点击低风险选项时可以直接向原 DSH 会话提交操作；涉及更高权限的选项则显示确认与具体执行范围。

### 10.3 个性化与角色风格

桌宠自己的语言可以活泼自然，但替用户生成的智能回复应尽量贴合用户的措辞与偏好。

用户的个人称呼、工作术语和沟通习惯可以保留。例如用户习惯称 Claude 为“小克”，系统提及该助手时可优先使用这个称呼。

角色个性不应影响执行报告的真实性。遇到失败、风险或不确定性时，必须清楚说明。

### 10.4 反打扰机制

默认只在重要进展、阻塞和必要决策时主动弹窗。

低优先级进度合并到摘要。允许勿扰时段、暂停消息、暂停自主执行、调整提醒密度。

用户未回复普通通知时，系统不得持续弹窗催促。

## 11. 技术架构

WhaleDot 建议由七个独立、可测试的模块组成：

| 模块 | 职责 |
|---|---|
| Pet Runtime | 透明窗口、角色动画、用户交互 |
| DSH Bridge | DSH 事件、会话、任务与工具接口 |
| Notification Center | 消息过滤、合并、持久化和显示 |
| Suggestion Engine | 智能回复、个性化、多选项推荐 |
| Goal & Memory Store | 项目目标、记忆、权限范围和检查点 |
| Autopilot Scheduler | 任务依赖、调度、状态机和恢复 |
| Action & Verification Gate | 操作校验、结果验收、继续或暂停判定 |

其中：

- Agent 推理、实际编码与工具调用尽量使用现有 DSH。
- 定时提醒复用 DSH 的 Schedule 能力；复杂项目调度由 WhaleDot 管理自己的任务队列。
- 使用 DSH 提供的公开事件、服务和插件扩展机制进行集成。
- 不直接修改 DSH 核心 Agent Loop。
- 用户授权与插件保存的目标状态分开管理。
- 所有重要执行步骤产生可追溯记录。

数据层至少需要持久化以下对象：

`ProjectGoal`、`AuthorizationScope`、`Task`、`Run`、`Checkpoint`、`Evidence`、`MemoryRecord`、`Notification`、`Suggestion`。

每次运行都有唯一的 `run_id`，每次尝试有 `attempt_id`，避免重试覆盖历史结果。

## 12. 开发路线

| 阶段 | 核心交付 | 验收目标 |
|---|---|---|
| M0：基础联通 | 桌宠窗口、角色动画、DSH 事件 | 桌面角色正确响应任务状态 |
| M1：桌面交互 | 主动提醒、多选项智能回复、一键提交 | 不打开 DSH 即可完成常见交互 |
| M2：Autopilot MVP | 自然语言目标、授权、三阶段自主推进 | 自主执行并验收三个依赖任务 |
| M3：持续任务 | 调度队列、持久化记忆、断点恢复 | 重启后能安全恢复项目目标 |
| M4：长期自治 | 目标跟踪、主动判断、停滞检测、动态建议 | 能长期推进而不产生失控循环 |
| M5：开源发布 | 安装、测试、文档、许可证、兼容性检查 | 干净 Windows 环境可复现安装和运行 |
| M6：生态扩展 | 语音、多设备、多角色、多 Agent | 可选插件独立安装和卸载 |

M2 开始必须保证自主推进闭环能够工作，不把核心能力推迟到遥远的高级版本。

## 13. 核心验收用例

公开版本至少验证以下场景：

1. 用户授权后，鲸鱼能够根据自然语言目标创建持续项目。
2. 连续执行三个前后依赖任务，中途不重复询问已经授权的常规操作。
3. 对超出授权范围的行为准确阻止并请求确认。
4. 任务完成后能找到实际证据，并正确判断是否达到验收标准。
5. 测试回归时停止不合理的继续执行。
6. 达到停滞限制后自动暂停，而不是循环生成相同任务。
7. 用户手动修改项目后，不会被后台任务静默覆盖。
8. 中途关闭并重启 DSH 后，任务记录和授权状态保持一致，不重复有副作用的操作。
9. 用户撤销授权后，新的自主执行无法越过权限边界。
10. 桌宠能够主动展示有价值的阶段结果和智能选项。
11. 个性化回复能够利用已确认的偏好，但不擅自改变实际操作意图。
12. 所有重要任务都能追溯到目标、执行记录、证据和结果。
13. 无效工具调用、模型错误和缺失验收记录不会被统计为成功。
14. 插件异常不会导致 DSH 核心无法正常启动。
15. 开源发布包中的角色素材和代码具有独立、明确的授权说明。

## 14. 质量评估指标

WhaleDot 本身需要独立的测试集与评估报告。

核心指标建议：

- **有效任务完成率**：完成且通过预定义验收的任务比例。
- **有效目标进展率**：在观察窗口内取得可核实进展的目标比例。
- **自主完成率**：无需额外人工干预而完成的授权内任务比例。
- **误操作率**：错误路由、重复执行或违反权限的操作比例。
- **回归率**：自动执行导致既有验收项失效的比例。
- **恢复成功率**：中断后能恢复一致任务状态的比例。
- **通知有用率**：用户确认有帮助的主动通知比例。
- **智能建议采纳率**：建议被接受及修改后的比例。
- **单位有效进展成本**：每项经验证成果消耗的模型与执行资源。
- **停滞识别准确性**：能否发现持续无提升的运行并及时停止。

所有结果应保留完整任务分母、失败、未知状态和运行版本。不能仅展示成功案例。

## 15. 首版不做的事情

为避免功能无限膨胀，第一轮开发不包括：

- 第二套自研 Coding Agent 或通用 Harness。
- 无限制自主执行和自我修改安全策略。
- 默认全屏观察或持续录屏。
- 无边界的个人信息采集。
- 没有明确验收标准的无限自我优化。
- 大型桌宠养成、商城和游戏系统。
- 强制要求用户连接云端账户。
- 一开始就引入复杂的多 Agent 层级架构。

这些功能不能影响首版核心闭环的交付。

## 16. v0.2 最终产品定义

**WhaleDot 是一个以桌宠为交互窗口、以 DeepSeek Harness 为执行引擎、以长期目标为工作中心的个性化主动 Agent。**

用户通过自然语言给出工作目标和允许的操作范围后，WhaleDot 会持续维护项目状态、主动推进任务、保存上下文、验证成果，并在需要用户决定时，通过桌面鲸鱼提供符合个人习惯的多选项智能回复。

它应当在用户不需要关注时安静工作，在有实质进展时主动汇报，在面对不确定性时及时求助，在超出授权边界时明确停止。

**WhaleDot v0.2 的第一优先级：让用户只需描述一次目标，就能看到一个真实项目在自己的授权范围内持续、可靠地向前推进。**
