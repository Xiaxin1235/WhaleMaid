# 项目雷达设计（1.5）

> 状态：已实现。与 1.4 的主动性闭环一起纳入 1.5.0。实现细节见 [P25 报告](p25-report.md)。

## 1. 要解决的问题

主动性引擎只看 WhaleMaid 自己的记录：目标、任务、执行和验收。但项目进展不一定都发生在自动推进里：依赖发了不兼容的新版本、你在别处改了代码、项目仓库的 CI 红了，这些都会影响正在推进的目标，WhaleMaid 现在看不到。

项目雷达要回答的只有一个问题：**这些外部变化，会不会影响我正在推进的目标？**

它不是新闻订阅器：只读、不改代码、不提 PR，发现的问题统一交给 1.4 的建议卡。

## 2. 原则与边界

| 原则                 | 含义                                                                                                        |
| -------------------- | ----------------------------------------------------------------------------------------------------------- |
| 默认不联网           | 雷达总开关默认关闭；每个目标在详情里看到“将观察的内容”，确认后才生效。                                      |
| 只读                 | 只读取注册表、GitHub 公开接口和本地 git 状态，不写任何外部系统，不修改项目文件。                            |
| 外部内容只当数据     | 发布说明、issue、PR、提交信息的正文都是数据，不当指令；建议卡正文用固定模板，不复述外部原文中的指令性文字。 |
| 规则优先，不调用模型 | 1.5 的“是否影响目标”判断全部基于规则；模型辅助判断留给 I4，单独开关和预算。                                 |
| 可见、可关           | 面板显示观察列表、最近检查时间、请求次数和失败原因；可按目标、按来源关闭。关闭不删除已有记录。              |

明确不做：研究资料与新闻源（以后配合模型辅助再议）、webhook 与常驻服务、自动升级依赖、自动开 issue 或 PR。

## 3. 观察的来源（首版 A、B、C）

| 来源                     | 内容                                                                                                | 获取方式                                                                                         | 联网 |
| ------------------------ | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ---- |
| A 依赖新版本             | 项目**直接**依赖的新版本：大版本更新、发布说明含 breaking / 破坏性字样、被标记弃用                  | npm registry、PyPI JSON 接口；依赖清单来自 `package.json`、`pyproject.toml`、`requirements*.txt` | 是   |
| B 本地外部改动           | 非 WhaleMaid 产生的提交、分支切换、未提交改动，以及改动是否碰到正在执行的目标的工作目录或受保护路径 | 本地 `git`（只读命令）                                                                           | 否   |
| C 项目自己的 GitHub 状态 | 默认分支 CI 结论、新开的 issue/PR（标题与改动的文件）                                               | GitHub REST 公开接口；远程地址来自项目的 `origin`                                                | 是   |

依赖版本优先查注册表而不是 GitHub：没有 GitHub 的调用次数限制，结果也更准确。

## 4. 订阅

- 在目标详情中新增“项目雷达”区块：自动识别项目的 git 远程地址和依赖清单，列出将要观察的内容（仓库、依赖个数、本地检查项），由你确认开启；可以逐项取消，或手动补充仓库地址。
- 订阅属于目标；目标完成或撤销授权后停止观察，记录保留。
- 雷达总开关关闭时，所有订阅都暂停，不删除。

## 5. 检查时机与限额

| 检查             | 时机                                                                                                               |
| ---------------- | ------------------------------------------------------------------------------------------------------------------ |
| B 本地 git       | 跟随现有主动性检测（事件触发、启动补做、每日首次检测），不联网，开销小                                             |
| A 依赖、C GitHub | **每天一次**（每个本地日首次检测时，且距上次检查 ≥ 24 小时）；宿主启动时若已超过 24 小时则补做；面板提供“立即检查” |

- GitHub 默认不带令牌（每小时 60 次额度）；请求带 ETag 条件缓存，内容未变时不重复下载。每个仓库每次检查只调少量接口。
- 可选：在 Harness 凭据存储中填写**只读**的 GitHub 令牌，用于观察更多仓库；令牌不进配置文件、不在面板显示、不写入日志。
- 遇到限流或网络失败：记录原因，下次检查再试，不重试刷屏；连续失败在面板显示，不发建议卡。

## 6. 新的检测器（交给 1.4 的建议卡）

| ID  | 机会             | 触发条件（初值）                                                             | 建议                                             | 默认最高分级 |
| --- | ---------------- | ---------------------------------------------------------------------------- | ------------------------------------------------ | ------------ |
| D8  | 依赖破坏性更新   | 直接依赖出现新的大版本，或新版本发布说明含 breaking 关键词，或当前版本被弃用 | 起草一个只读的“升级影响排查”目标（仍需审核授权） | L2           |
| D9  | 默认分支 CI 失败 | 默认分支最近 ≥2 次 CI 结论为失败，且目标仍活跃                               | 暂停相关目标，或起草只读排查目标                 | L2           |
| D10 | 外部改动冲突     | 出现非 WhaleMaid 的改动，且碰到正在执行的目标的工作目录或受保护路径          | 询问：继续、暂停，还是先查看改动                 | L3           |
| D11 | 相关 issue/PR    | 新 issue/PR 的标题或改动文件与目标涉及的路径匹配                             | 只进简报                                         | L1           |

- 证据只存引用（包名与版本、CI 运行 ID、issue 编号、提交哈希）和摘要哈希；外部正文按需读取并截断显示。
- 去重键包含版本号、运行 ID 或提交范围，同一变化不重复提醒；沿用 1.4 的冷却、合并、反馈和自动降级。
- 效果评测沿用 1.4 的指标，另加“检查成功率”和“每日请求数”。

## 7. 数据

- `radar_subscriptions`：目标、来源类型、对象（包名、仓库）、状态、确认时间。
- `radar_observations`：每次检查的结果快照（版本、CI 结论、HEAD、请求次数、ETag、失败原因），只保留最近若干条。
- 机会仍写入 `opportunities`，由 D8–D11 产生。

## 8. 测试要点

- 依赖清单解析：npm 的各种版本范围、Python 的常见写法；只取直接依赖。
- 版本比较与 breaking 判定：表驱动测试，覆盖预发布版本、0.x 版本（0.x 的次版本变化视为破坏性）。
- 网络层可替换：所有外部请求通过可注入的客户端，测试用录制好的响应；限流、超时、304 都有用例。
- 本地 git：在临时仓库中构造外部提交、分支切换、碰到受保护路径的改动，确认 D10 只在真正冲突时触发。
- 安全：发布说明或 issue 中带有“请执行……”之类的文字时，不会进入任何执行路径，建议卡正文不复述原文。

## 9. 已确定与待讨论

已确定：

- **D10 询问期间暂停该目标的自动推进**：出现外部改动冲突时，该目标的调度器跳过新的执行，直到你回答（继续、暂停或先查看改动）；已在进行中的执行不强行中断，按现有规则收尾。这是调度器行为的变化，需要单独测试：暂停只作用于该目标，其他目标照常推进，回答“继续”后立即恢复。暂停不依赖提醒渠道：即使 L3 询问渠道关闭（1.4 的默认值），D10 仍会暂停该目标，并改用建议卡给出同样的三个选项；建议卡也关闭时，在面板与目标详情显示“等待你确认外部改动”。
- D11 首版只用路径和标题关键词判断相关性，只进简报；误报多时再收窄。
- 首版只支持 npm 和 PyPI 的依赖清单。

待讨论：暂无。可以据此写 1.5 的实现提示词（在 1.4 合入后）。
