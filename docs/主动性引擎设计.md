# 主动性引擎设计（草案）

> 状态：设计草案，尚未实现。对应《项目规划》F08 主动个人 Agent、F10 主动性和智能建议优化。

## 1. 要解决的问题

WhaleMaid 现在的主动性只有一种：**出了事来找你**。目标停滞会暂停并请你决定，验收失败会发决策卡，每日简报在你开口时汇报进展。它不会**发现机会来找你**：同一个错误在三个任务里反复出现、某个目标一直没有可用的验收命令、预算快用完而进度还停在一半，这些事都要你自己发现。

主动性引擎要补上的是这一层：从 WhaleMaid 已经掌握的结构化事实中，找出“值得现在提一下”的事，判断要不要打扰你、以什么方式打扰，并根据你的反应调整以后的判断。

一句话：**主动性 = 发现机会 + 判断价值 + 选择行动 + 反馈学习**。

## 2. 原则与边界

| 原则               | 含义                                                                                                                                                        |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 只提建议，不扩权   | 引擎只能记录、汇报、提出建议或询问。任何执行仍走现有的确认通道（面板审核、`CompanionActions.propose` 的本人确认、原生审批），不能自动扩大授权、预算或范围。 |
| 规则优先，模型可选 | 第一阶段的发现与评分全部基于规则，不增加模型调用。模型辅助判断放到后续阶段，并单独计入调用预算。                                                            |
| 有证据才开口       | 每条建议都要引用具体的记录（验收 ID、任务 ID、通知 ID），面板能点进去核对。不根据想象或推测开口。                                                           |
| 少打扰优先于多发现 | 打扰预算比发现能力更重要。宁可漏报，也不要把通知中心变成噪声。所有主动建议都受现有勿扰、静音和每小时上限约束。                                              |
| 用户能关、能调     | 每个检测器、每种提醒渠道、大肥鱼的每种表现都有独立开关，各级别的限制可调。关闭后已有记录保留，不再产生新建议。                                              |

明确不做：自动开启新目标、自动追加预算、替你在决策卡上选择、根据读到的会话或文件里的“要求”行动（这些仍只当作数据）。

## 3. 现有可复用的部件

| 部件                                         | 现状                                                         | 在引擎中的用途                                           |
| -------------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------- |
| `verifications`、`attempts`、`runs`、`tasks` | 每次执行和独立验收的结论、命令、输出摘要与预算消耗           | 主要信号源：反复失败、无验收依据、预算消耗速度           |
| `autopilot_events`、`state_transitions`      | 目标与任务的状态变化、暂停、停滞计数                         | 停滞前兆、长期闲置                                       |
| `notifications` 与 `decideDelivery`          | 通知记录和统一的打扰策略（勿扰时段、静音、每小时上限、去重） | 直接复用投递；策略已支持目标通知以外的类型（如记忆提议） |
| `suggestions`                                | 智能选项按你以往的选择调整排序                               | 反馈学习的先例：记录选择结果并据此调整                   |
| `memory_proposals` 与项目经验草稿            | 事件触发、去重、限频、过期、逐条确认                         | 机会的生命周期可照搬这套模式                             |
| `companion_journal`（她的经历）              | 由结构化记录生成，不调用模型                                 | 第二阶段让大肥鱼的经历包含“发现了什么、你怎么回应的”     |
| 每日简报                                     | 每天第一次真实回合注入固定快照，不调用模型                   | 低优先级的发现进简报，不单独打扰                         |
| `CompanionActions.propose`                   | 管理动作由宿主向本人确认后执行                               | 用户采纳建议时，复用它执行暂停、备注等已有动作           |

## 4. 总体流程

```text
信号（已有表的增量）
  → 检测器（规则，每个只认一类机会）
  → 候选机会（带证据、主题、去重键）
  → 评分与去重（价值、置信度、冷却期）
  → 行动分级（L0 记录 / L1 进简报 / L2 建议卡 / L3 请求许可）
  → 投递（复用 decideDelivery 和通知中心、桌宠信封）
  → 反馈（采纳 / 稍后 / 忽略 / 不再提醒这类事 / 过期）
  → 调整（检测器阈值、分级、冷却期）
```

### 4.1 触发时机

不常驻轮询模型。检测在以下时机运行，每次只读增量：

- 验收结论写入、任务或目标状态变化之后（事件驱动，延迟合并 30 秒，避免一连串事件触发多次）；
- 宿主启动补做一次；
- 每天本地时间首次检测（用于“长期闲置”“待决定积压”这类按时间判断的机会）。

### 4.2 机会（Opportunity）

```ts
interface Opportunity {
  id: string
  detector: DetectorId // 产生它的检测器
  subject: { goalId?: string; taskId?: string } // 关于哪个目标或任务
  dedupeKey: string // detector + subject + 证据签名
  evidence: EvidenceRef[] // 指向 verifications / tasks / notifications 的 ID，不复制正文
  summary: string // 固定模板生成，不调用模型
  score: number // 0–1
  level: 'L0' | 'L1' | 'L2' | 'L3'
  actions: OpportunityAction[] // 采纳时可选的已有动作，如“暂停目标”“添加备注”“打开详情”
  status: 'open' | 'delivered' | 'accepted' | 'snoozed' | 'dismissed' | 'muted' | 'expired'
  createdAt: number
  expiresAt: number
  outcomeAt?: number
}
```

新增 `opportunities` 表保存上述字段；`evidence` 只存 ID 和摘要哈希，正文按需从原表读取，删除原记录后证据显示为“已删除”。

## 5. 第一批检测器（全部基于规则）

| ID  | 机会               | 触发条件（初值，可调）                                                                             | 建议内容                                                 | 默认分级 |
| --- | ------------------ | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------- | -------- |
| D1  | 同一原因反复失败   | 同一目标内，验收失败的命令与输出签名（去掉路径、时间、数字后的哈希）在 ≥3 个任务或 ≥3 次尝试中重复 | “可能不是代码问题，建议先检查环境/数据/依赖”，附三次证据 | L2       |
| D2  | 停滞前兆           | 进度连续“无变化”的轮数达到 `maxStallRounds - 1`，即将被自动暂停                                    | 提前建议拆分任务、补充备注或调整验收命令                 | L2       |
| D3  | 缺少可用验收依据   | 目标中出现 ≥2 个 `NOT_SCORABLE` 任务，或 report-only 任务占比 ≥50%                                 | 建议补充可执行的验收命令（需在面板重新审核授权）         | L1       |
| D4  | 预算消耗过快       | 已用尝试或时间预算 ≥80%，而通过的任务 ≤50%                                                         | 询问是否收尾、调整目标或追加预算（追加仍须在面板确认）   | L3       |
| D5  | 待决定积压         | 有决策卡投递后 24 小时未处理，且该目标因此停着                                                     | 进简报；48 小时后升级为一条提醒                          | L1 → L2  |
| D6  | 已授权目标长期闲置 | 授权有效、未完成，但自动推进关闭或暂停 ≥7 天                                                       | 问是继续、暂停到某天，还是放着不管（放弃仍须在面板操作） | L1       |
| D7  | 完成后的遗留       | 目标完成，但最终报告的结构化字段里有“未完成/后续”条目，或存在被跳过的任务                          | 列出遗留项，建议是否起草后续目标（起草仍走现有流程）     | L1       |

D1 是第一阶段最有价值的一条：它对应“多轮实验指标不变，应该先检查数据版本，而不是继续跑”这种场景，而且完全可以从现有验收记录里判断。

## 6. 价值评分与分级

```text
score = 严重度 × 置信度 × 相关度 × 新颖度
```

- **严重度**：由检测器定义，例如 D4 预算将尽 > D1 反复失败 > D6 闲置。
- **置信度**：证据数量和一致性，例如 D1 中重复次数越多越高。
- **相关度**：目标当前活跃为 1，暂停中为 0.6，已完成为 0.4。
- **新颖度**：同一去重键在冷却期内出现过则为 0；被“稍后”过的按剩余等待时间折减。

| 分级 | 表现                                         | 打扰                                 |
| ---- | -------------------------------------------- | ------------------------------------ |
| L0   | 只记录，在面板“发现”列表中可见               | 不打扰                               |
| L1   | 进每日简报，由大肥鱼在你开口时顺带提一句     | 不单独打扰                           |
| L2   | 通知中心 + 桌宠信封里的建议卡，带可点选项    | 受 `decideDelivery` 和 L2 的分级限制 |
| L3   | 需要你决定才能继续的询问（原生提问或决策卡） | 同 L2，但不进入摘要合并              |

分级由检测器默认值和得分共同决定：得分低于 0.3 一律降为 L0。

## 7. 打扰预算

不设主动建议的总次数上限，而是**按重要程度分级限制**：越重要的越少受限，越不重要的越要合并或延后。每一级的限制都可在面板调整。

| 分级 | 默认限制                                                                | 理由                                           |
| ---- | ----------------------------------------------------------------------- | ---------------------------------------------- |
| L0   | 不限                                                                    | 只记录，不打扰                                 |
| L1   | 不限条数；简报里最多列 3 条最高分的，其余在面板“发现”列表               | 简报要短，否则就不再是简报                     |
| L2   | 同一目标两张建议卡之间至少间隔 4 小时；间隔内新出现的机会合并进下一张卡 | 建议可以等，按目标限流避免一个出问题的目标刷屏 |
| L3   | 不限次数，但同一件事不重复问；勿扰时段内暂存，结束后投递                | 不问就无法继续，限次数只会让目标白白停着       |

所有级别共用三条规则：

1. **冷却期**：同一去重键被投递后 7 天内不再投递；选了“不再提醒这类事”的检测器，对该目标永久静默，可在面板恢复。
2. **合并**：同一目标同一次检测产生的多条机会合并为一张卡，按得分排序列出。
3. **共用通知策略**：L2/L3 作为新的通知类型 `initiative` 交给 `decideDelivery`，勿扰时段、静音、去重自动生效。现有的“每小时上限”（默认 4 条）对所有通知一起计算，是唯一的总量上限；觉得太少可在通知中心调高。

## 8. 反馈与学习

每张建议卡都提供固定的四个反馈：**采纳**（执行所选的已有动作）、**稍后**（指定时间再提）、**忽略**（这次不处理）、**不再提醒这类事**。卡片过期未处理记为“无回应”。

| 指标                   | 定义                                                     | 用途                                 |
| ---------------------- | -------------------------------------------------------- | ------------------------------------ |
| 采纳率                 | 采纳 ÷ 已投递                                            | 面板展示；低于阈值时自动降级检测器   |
| 无效打扰率             | （忽略 + 不再提醒 + 无回应）÷ 已投递                     | 超过 50% 时该检测器默认降为 L1       |
| 带来的进展             | 采纳后 48 小时内，相关目标出现新的 PASS 或状态推进的比例 | 判断建议是否真的有用，而不只是被点了 |
| 每条有效建议的模型成本 | 第一阶段恒为 0；后续阶段统计模型调用                     | 控制模型辅助检测的成本               |

自动调整只做两件可解释、可撤销的事：调整检测器的默认分级，以及在规定范围内调整阈值（例如 D1 的重复次数 3 → 4）。每次调整写入追溯记录，面板可以恢复默认值。

## 9. 与大肥鱼的衔接

第一阶段只用现有渠道（通知卡、信封、简报），大肥鱼在伙伴对话里可以查询“最近发现了什么”。

第二阶段让“主动”和“陪伴”连起来，仍然不新增模型调用：

- **经历**：被采纳的发现和结果写入 `companion_journal`，例如“发现三次失败都是同一个依赖缺失，你采纳了建议，之后测试通过”。她的经历因此来自真实发生的事。
- **收工汇报**：当天有被采纳的建议或完成的目标时，在你设定的收工时间（默认关闭）用固定模板发一条 L1 级汇报，不在勿扰时段发。
- **安静陪伴**：当天已经主动打扰过 2 次、或你在勿扰时段内，她只在你主动开口时才提发现。

## 10. 配置

每个功能都有独立开关，在面板“主动性”卡片中按三组展示。总开关关闭时其余开关保留设置但不生效；关闭任何开关都不删除已有记录。

**发现什么**：每个检测器一行，可单独开关，并单独设定最高分级（检测器的建议不会超过这一级）。

| 配置                                   | 默认开关 | 默认最高分级 |
| -------------------------------------- | -------- | ------------ |
| `initiative.detectors.repeatedFailure` | 开       | L2           |
| `initiative.detectors.stallWarning`    | 开       | L2           |
| `initiative.detectors.noAcceptance`    | 开       | L1           |
| `initiative.detectors.budgetBurn`      | 开       | L3           |
| `initiative.detectors.pendingBacklog`  | 开       | L2           |
| `initiative.detectors.idleGoal`        | 开       | L1           |
| `initiative.detectors.leftovers`       | 开       | L1           |

**怎么告诉你**：每种渠道一个开关。关闭某个渠道后，原本走这个渠道的建议降一级处理；L1 也关闭时只留在面板。

| 配置                        | 默认      | 说明                             |
| --------------------------- | --------- | -------------------------------- |
| `initiative.enabled`        | 开        | 总开关；关闭后不检测、不投递     |
| `initiative.channels.brief` | 开        | L1：进每日简报                   |
| `initiative.channels.cards` | 关        | L2：建议卡（通知中心与桌宠信封） |
| `initiative.channels.asks`  | 关        | L3：需要你决定的询问             |
| `initiative.limits.*`       | 见第 7 节 | 各级别的限制参数，可逐项调整     |

**大肥鱼怎么表现**（第三阶段）：

| 配置                                 | 默认 | 说明                                                    |
| ------------------------------------ | ---- | ------------------------------------------------------- |
| `initiative.companion.journal`       | 开   | 被采纳的发现写入她的经历                                |
| `initiative.companion.findings`      | 开   | 伙伴对话中可查询“最近发现了什么”                        |
| `initiative.companion.eveningReport` | 关   | 收工汇报时间，如 `21:00`                                |
| `initiative.companion.quiet`         | 开   | 当天已打扰过 2 次或处于勿扰时段时，只在你开口时才提发现 |

建议卡和询问默认关闭，是为了先让用户在面板里看看检测质量，再自己决定要不要被主动打扰。首次打开“主动性”卡片时，用一句话说明三个渠道的区别。

## 11. 分阶段计划

| 阶段 | 内容                                                                                   | 模型调用 | 完成标准                                                                   |
| ---- | -------------------------------------------------------------------------------------- | -------- | -------------------------------------------------------------------------- |
| I1   | `opportunities` 表；D1–D7 检测器；评分与分级；L0/L1 投递；面板“发现”列表与指标         | 无       | 用固定的验收与状态记录做测试，每个检测器的触发、不触发、去重、冷却都有覆盖 |
| I2   | L2/L3 建议卡；四种反馈；分级限制；自动降级；`initiative` 通知类型接入 `decideDelivery` | 无       | 隔离环境中走通“发现 → 建议卡 → 采纳 → 执行已有动作 → 追溯”，勿扰和上限生效 |
| I3   | 大肥鱼的经历与收工汇报；伙伴工具“查询最近发现”                                         | 无       | 经历中的每条发现都能追溯到原始记录                                         |
| I4   | 模型辅助检测：读取工作对话的最近步骤，判断是否偏离目标；可选外部信息源作为检测器       | 有，计数 | 单独的调用预算和开关；低于采纳率阈值自动停用                               |

I1 和 I2 不依赖桌宠；没有桌宠时，建议卡在 WhaleMaid 通知中心和 Harness 通知会话里处理。

## 12. 测试要点

- 检测器是纯函数：输入为固定的表记录快照，输出为机会列表，不读时钟（时间作为参数传入），便于构造边界用例。
- 失败签名的归一化要单独测试：同一错误在不同路径、行号、时间戳下应得到相同签名；不同错误不应碰撞。
- 打扰预算与现有通知共用策略，需测试两者叠加时的总量不超过每小时上限。
- 开关与分级的组合：检测器最高分级、渠道开关、分级限制三者叠加后的最终分级是一个纯函数，用表驱动测试覆盖“渠道关闭时降级”“检测器上限低于得分分级”“L3 在勿扰时段暂存”等组合。
- 反馈与自动降级：构造 10 次投递、2 次采纳的序列，确认检测器被降级并留下追溯记录，面板可以恢复。
- 安全：建议卡上的选项只能映射到已有的管理动作；伪造或过期的选项被拒绝，与现有智能选项的结算规则一致。

## 13. 实现成本

独立开关和分级限制不改变引擎的核心逻辑，增加的工作集中在三处：

| 部分         | 增加的工作                                                             | 估计         |
| ------------ | ---------------------------------------------------------------------- | ------------ |
| 配置与校验   | 嵌套的开关和限制参数，沿用现有 Schemastery 配置写法                    | 小           |
| 最终分级计算 | 检测器上限、渠道开关、分级限制叠加成一个纯函数；由它决定每条机会的去向 | 小，测试为主 |
| 面板设置     | “主动性”卡片的三组开关、每个检测器的分级下拉、限制参数，以及恢复默认   | 中，最费时   |

其余部分（检测器、评分、投递、反馈）与原方案相同。主要的额外风险是开关组合多，用表驱动测试覆盖即可。

## 14. 待讨论

1. 第 10 节各开关的默认值是否合适，尤其是建议卡和询问默认关闭。
2. D1 的失败签名是否要包含验收命令的退出码以外的输出片段；输出可能含敏感信息，只存哈希是否足够。
3. 收工汇报用固定模板还是允许一次模型润色；后者会把“不增加模型调用”的承诺打破，需要单独开关。
4. 是否把“不再提醒这类事”做成跨目标的全局设置，还是只对当前目标生效。
