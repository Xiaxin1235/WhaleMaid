# P21 WhaleMaid：决策提问可靠投递与选项修正

**前置**：主动性引擎第一阶段（I1）已在本地提交，工作区干净（本提示词文件除外）。先跑一遍 `pnpm install --frozen-lockfile`、`pnpm build`、`pnpm test`，确认基线通过。I1 还没提交时**不要开始**：两者都会改 `store`、`index.ts`。

> **改名说明**：项目已从 WhaleDot 改名为 WhaleMaid（包名 `dsh-whalemaid`、`@whalemaid/core`）。以下内容**有意保持旧名**，不要改：本地目录 `D:\dsh_plugins\WhaleDot`、插件配置 ID 和数据目录 `whaledot`、大肥鱼预设 `whaledot-companion`、隔离 profile `whaledot-p02`。

## 背景

用户反馈：推进项目时，“给几个选项”的提问触发不稳定，该弹的时候没弹，弹出来的选项有时也不对。读代码发现以下几个疑点（尚未实测确认，先查证）：

1. **只尝试一次**：`packages/core/src/notify/policy.ts` 的 `decideDelivery` 中，`deliveryAttemptedAt` 已设置、且没有更晚的 `remindAt` 时，一律返回 `drop: already-attempted`。`packages/host/src/notify/deliverer.ts` 的 `send()` 失败时只恢复 `deliveredAt`，不清 `deliveryAttemptedAt`，所以**投递失败后不会再弹**。
2. **取消后也不再弹**：以下情况会中止正在进行的提问，状态记为 `cancelled`，之后同样因第 1 条被丢弃：
   - 宿主停止（`dispose()` 中的 `notifier-disposed`），也就是 DSH 或 Harness 重启；
   - 打开静音（`cancelInvalid()` 检查 `muted`）；
   - 任务版本变化（`valid()` 要求 `taskVersion` 一致）。
   结果是：决策仍然需要处理，但桌宠不会再问，只剩面板通知中心里能看到。
3. **选项被截断**：`packages/core/src/notify/suggestions.ts` 的 `buildSuggestions` 中，业务选项按固定优先级只取前两个（`.slice(0, 2)`），`change-direction` 排第一、`accept` 排最后。所以验收决策（`retry`/`accept`/`rollback`/`pause-goal`/`view-diff`）和 `verification-unknown`（`verify`/`accept`/`pause-goal`）在加入“改方向”后，往往**看不到“接受”**。
4. **24 小时过期**：`verify-task.ts` 与 `goal-notices.ts` 建的决策通知都是 `expiresAt = 创建 + 24h`。需要确认：过期后目标是否仍卡在等待决策，有没有新的通知接替。如果目标仍在等，就等于决策机会丢了。

## 目标

- **可靠性**：仍需用户处理的决策，必须始终能在面板看到；在能安全提问时（服务可用、未静音、不在免打扰时段、授权有效），桌宠会重新提问，直到被处理、被取代或真正失效。
- **不打扰**：用户看到但没回答的提问，不会反复骚扰。“看到但没答”与“没送达或被系统取消”必须区分处理。
- **选项合理**：每类决策的关键操作一定出现，总数 2–4 个。
- **可追查**：每条决策为什么弹了、为什么没弹，都能在面板和日志里看到。

## 先查证（写进报告，附代码出处）

1. 背景中第 1–4 条是否属实；有不一致的，以代码为准。
2. `inbox.ask()` 的几种结束方式分别对应什么：用户回答、用户关掉问题、Harness 客户端离线（桌宠显示“请在 Harness 里处理”）、会话被删除、服务不可用。能否区分“用户看到后主动关闭”和“系统原因中断”？区分不了时如何保守处理，写明。
3. 任务版本变化的常见来源：哪些版本变化不影响决策（例如只写了进度、追加了日志），哪些会让决策失效（状态已经转移、已被另一个界面处理）。
4. 决策通知过期后，目标和任务处于什么状态；`verify-task.ts` 的去重键（含 `taskVersion`）在什么情况下会重建通知。
5. 面板和桌宠同时操作同一个选项时，现有的“先持久认领、再执行”是否已能保证只执行一次（`router.route`）。本任务**不能削弱**这一点。

## 实现

### 1. 投递状态与重试（core `policy.ts`，host `deliverer.ts`）

- 把“尝试过就丢弃”改为按结束原因处理：
  - **已回答 / 已处理**：结束，不再问（现状）。
  - **用户看到后主动关闭、没有选择**：不自动重问，保留在面板；用户点“稍后提醒”时按现有 `remindAt` 规则再问。
  - **投递失败**（服务不可用、会话准备失败、`question-service-failed`）：按退避重试，例如 1 分钟、5 分钟、30 分钟，之后每 2 小时一次；重试只在“能安全提问”的条件下发生，并计入 `maxPerHour`。
  - **系统取消**（宿主停止、静音、免打扰开始）：恢复后重新提问，不计入失败次数。
  - **任务版本变化**：重新核对决策是否仍然需要。仍需要的，用当前版本重建选项并重新提问（新的一代，旧选项作废）；不再需要的，标记为 `superseded` 并在面板说明原因。
- 这些都用持久字段记录（例如尝试代数、失败次数、下次重试时间、结束原因），宿主重启后能接着处理。字段加迁移，不改动已有记录的含义。
- 保持现有约束：同一目标同一时间只有一个提问在进行；投递认领在事务里；旧一代选项不能生效。

### 2. 决策的有效期

- 根据查证第 4 条决定：目标仍在等待这条决策时，通知不应因为 24 小时到期而消失。可以改成“目标仍在等待就保持打开”，或者到期时生成接替的通知。选一种，在报告里说明理由。
- 授权过期或被撤销时，决策照旧失效，面板说明原因。

### 3. 选项选择（core `suggestions.ts`）

- 按决策类型定义“必须出现”的选项，再按优先级补足，总数 2–4 个：
  - 验收决策：`accept` 和 `retry` 必须有；有 `rollback` 时作为第三个；
  - `verification-unknown`：`verify` 和 `accept`；
  - 阻塞 / 停滞类：`resume-goal` 或 `retry`，以及 `change-direction`（如果合法）；
  - `pause-goal`、`view-diff`、“稍后提醒”、“打开面板”按剩余名额补充。
  - 具体映射以查证时看到的实际 `reason` 和 `choices` 为准，写成一张表放进代码常量和报告。
- 只从该通知合法的 `choices` 中选，不新增操作类型，不调用模型。
- 历史频率排序只调整顺序，不能把“必须出现”的选项挤掉。高风险选项（`accept`/`rollback`/`abandon`）保留现有的确认和授权校验。

### 4. 投递记录与面板

- 每次决策的投递过程写入现有 `notificationDeliveries`（或在其上扩展）：生成、被策略压住（含原因：静音、免打扰、每小时上限、重复）、开始提问、已回答、用户关闭、失败（原因）、系统取消（原因）、已取代、已过期。
- 面板通知中心的每条决策，显示当前投递状态和下一次提问时间，例如“静音中，解除后再问”、“投递失败，5 分钟后重试”、“已过期：任务已被另一个界面处理”。中英文文案齐全。
- 调试日志不写提问正文和用户输入，只写 ID、状态和原因。

## 不要做

- 不让模型生成或挑选选项，不在投递判断中调用模型。
- 不做“值得建议但不必问”的主动建议卡，那属于主动性引擎 I2。
- 不放宽授权、版本、作用域校验，不改执行、验收、停滞判断的逻辑。
- 不改动 `../dsh-coopanion`。
- **不要推送到 GitHub**，只在本地提交。

## 测试

- `decideDelivery` 表驱动：各结束原因 × 静音 / 免打扰 / 每小时上限 / 重复 / 稍后提醒 / 过期。
- 故障注入回归（建议写成一组可循环的场景测试，每个场景跑多轮，随机组合事件顺序）：
  - 提问服务抛错后按退避重试，恢复后成功提问一次；
  - 提问进行中宿主停止，重启后重新提问；
  - 提问进行中开启静音，解除静音后重新提问；
  - 任务版本变化但决策仍需要：重建选项，旧选项提交返回失效；
  - 任务已被面板处理：桌宠的提问被取消且不再出现；
  - 用户关闭提问不选：不自动重问，“稍后提醒”到点后再问；
  - 面板与桌宠同时提交同一决策：只执行一次；
  - 决策超过 24 小时目标仍在等待：按第 2 节规则保持可处理。
- 验收标准：所有仍需处理的决策都能从面板看到；同一决策不会执行两次；失效选项不能生效；没回答的提问不会被反复追问；普通进度不会因此多发通知。
- 选项选择：每类决策的必须选项都在，总数 2–4，频率排序不挤掉必须选项。
- 存储迁移：从现有数据库升级不丢数据，旧的 `already-attempted` 记录按新规则处理时不会一次性全部重弹（只重问仍需处理、且未被用户关闭的）。
- 全量 `pnpm test`、`pnpm typecheck`、`pnpm lint`、`pnpm format:check` 通过。

## 隔离实测

在隔离环境 `whaledot-p02`（`.dsh-dev`，端口 3182，**不碰日常 profile，不在设了 DSH_HOME 的终端里启动桌面版 Harness**）里：

1. 让一个目标产生验收决策，确认桌宠提问里有“接受”。
2. 提问进行中重启隔离宿主，确认重启后重新提问，面板显示投递经过。
3. 开静音再解除，确认解除后重新提问。
4. 在面板处理掉决策，确认桌宠的提问消失且不再出现。
5. 记录面板通知中心投递状态的实际显示（截图或文字）。
