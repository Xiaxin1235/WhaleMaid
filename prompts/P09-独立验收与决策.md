# P09 独立验收 + 决策 + 范围守卫（M2）

## 第零部分：P08 审查遗留（先做，单独提交）

### 1. 【高危】shell 读文件命令绕过路径授权

已在本机用构建产物复现（`checkAction`，`allowedPaths: ['D:/proj']`，cwd 为 `D:/proj`，read-only 预设）：

| 命令 | 现在的结果 |
|---|---|
| `type C:/Users/xx/.ssh/id_rsa` | allow（rule `read-command-allowed`） |
| `Get-Content C:/Users/xx/.dsh/profiles/desktop/cordis.patch.yml` | allow |
| `cat D:/proj/.env` | allow（protectedNames 也没生效） |

原因：P08 按提示词要求让 `READ_ONLY_COMMAND` 在 cwd 获准时直接 allow，但这些命令的**路径参数**没有经过 `isPathAllowed`。这是提示词的疏漏，需要修正：

- core：为只读命令建立参数解析——`classifyCommand` 之外新增 `readOnlyCommandPaths(cmdline, cwd) → { paths: string[] } | { unparsable: true }`，覆盖 `READ_ONLY_COMMAND` 中所有带路径的写法（`Get-Content`/`cat`/`type` 的文件参数，`Get-ChildItem`/`ls`/`dir` 的可选目录参数，含引号路径、`-Path`/`-LiteralPath` 命名参数、相对路径以 cwd 解析）。解析不了 → 不当作只读命令（走 `verifyCommands` 精确匹配，否则 ask → 门禁 deny）。
- `checkAction` 的 `run-command`：只读命令的每个路径都必须 `isPathAllowed`（含 protectedPaths 与 protectedNames）；无参数的列目录命令视为对 cwd 的访问。
- host 门禁：对这些路径同样先 `resolveRealTarget` 再检查（与文件工具一致）。`Get-ChildItem`/`ls`/`dir` 列目录时，被列目录下的直接子项也要通过 protectedNames 检查（避免把受保护文件名列出来也可以接受，但**不得读出内容**——至少保证内容读取类命令被拒）。
- 测试：上表三条 + 引号路径 + `-LiteralPath` + 相对路径 `..\..\secret` + UNC + 无参数 `dir` 在 cwd 内 → allow + `Get-Content .env` → deny。

## 第一部分：core（纯函数，带测试）

### 1. 测试结果解析 `packages/core/src/verify/parse.ts`
- 输入：命令、退出码、是否超时、stdout/stderr 尾部（已截断）。
- 输出 `CommandResult { command, status: 'passed'|'failed'|'error'|'timeout', exitCode, counts?: { passed, failed, skipped } }`。`error` = 进程没能启动或被信号杀死。
- `counts` 只对认得出的格式提取（vitest、jest、pytest、mocha 的摘要行，各写夹具），认不出就不给 counts，不猜。

### 2. 验收判定 `packages/core/src/verify/judge.ts`
`judge(input) → { verdict: 'PASS'|'FAIL'|'INSUFFICIENT_EVIDENCE'|'NOT_SCORABLE'|'UNKNOWN', reasons: string[], progress: 'improved'|'unchanged'|'regressed'|'unknown' }`，输入包括：任务类型、运行结果（结束原因、被门禁拒绝次数）、改动文件列表、基线结果（运行前提交上的验收结果）、当前结果（检查点提交上的验收结果）、最终回复是否非空。

规则（每条写测试）：
- 任一验收命令 `error`/`timeout`，或基线/当前缺失 → `UNKNOWN`（不是失败也不是成功）。
- `analyze`/`research`：有文件改动 → `FAIL`（分析任务不应改代码）；无改动且最终回复非空 → `PASS`，并标注 reasons 含 `report-only`；最终回复为空 → `INSUFFICIENT_EVIDENCE`。
- `edit`/`test`/`doc`：
  - 没有配置任何验收命令 → `NOT_SCORABLE`（需要用户看 diff 决定）。
  - 没有任何改动 → `INSUFFICIENT_EVIDENCE`。
  - **回归**：某命令基线 `passed`、当前 `failed`，或 counts.failed 增加，或 counts.passed + failed 总数减少（疑似删测试/改分母）→ `FAIL`，progress `regressed`。
  - **验收篡改（Scope Guard）**：改动中删除了测试文件；新增 `.skip(`、`.only(`、`xit(`、`xdescribe(`、`@pytest.mark.skip`、`pytest.skip(` 等；修改了与验收命令相关的配置（`package.json` 中被验收命令调用的 scripts、`vitest/jest/pytest` 配置文件）→ `FAIL`，reasons 含 `acceptance-tampering`，并且**不允许自动重试**（必须用户决定）。
  - 全部通过 → `PASS`；failed 计数下降或有命令从 failed 变 passed → progress `improved`；否则 `unchanged`。
  - 仍有失败但无回归、failed 计数下降 → `PASS`（任务验收通过），progress `improved`。
  - 仍有失败、无回归、无改善 → `FAIL`，progress `unchanged`。
- 门禁拒绝次数 > 0 不直接判失败，但写入 reasons（`denied-actions:N`），供决策参考。

### 3. 下一步决策 `packages/core/src/verify/decide.ts`
`decideNext(input) → Decision`，输入：判定结果、任务尝试次数、limits、目标的连续“无进展”轮数、是否篡改。输出之一：
- `succeed`（→ `SUCCEEDED`）；
- `retry`（→ `FAILED` → `READY`，attempts+1，下次提示词附带失败摘要）——仅当 FAIL、非篡改、非回归、`attempts < maxFixRounds`；
- `rollback-and-retry`（回归时：回滚该运行的改动后重试，同样受 `maxFixRounds` 限制）；
- `ask-user`（→ `WAITING_APPROVAL`，附决策类型：`not-scorable` / `insufficient-evidence` / `tampering` / `fix-rounds-exhausted` / `stalled`）；
- `reconcile`（UNKNOWN：先核对外部状态，见第二部分 3）；
- `pause-goal`（连续无进展轮数达到 `maxStallRounds`：目标转 paused，并 ask-user `stalled`）。
同时输出 `goalProgress` 更新（连续无进展计数的增减规则写清楚：`improved` 清零，`PASS`+`unchanged` 加一，`FAIL` 不清零）。

## 第二部分：host

### 1. 验收执行器 `packages/host/src/verify/runner.ts`
- 在 worktree 中按 `scope.verifyCommands` 的顺序逐条运行**用户确认过的精确字符串**（Windows 下经 `cmd.exe /d /s /c` 执行该字符串；只允许 `classifyCommand` 不为 `forbidden` 的命令，执行前再检查一次）。
- **环境变量净化**：子进程只继承白名单变量（`PATH`、`PATHEXT`、`SystemRoot`、`ComSpec`、`TEMP`、`TMP`、`USERPROFILE`、`HOME`、`APPDATA`、`LOCALAPPDATA`、`ProgramFiles*`、`NUMBER_OF_PROCESSORS`、`OS`、`PROCESSOR_*`、`CI=1`），并剔除名字匹配 `/KEY|TOKEN|SECRET|PASSWORD|CREDENTIAL|COOKIE/i` 的变量。理由：验收命令会执行项目代码，不能让它读到模型 API Key 等凭据。
- 超时 = `limits.maxRunMinutes`；超时杀掉整个进程树（Windows 用 `taskkill /T /F /PID`），结果 `timeout`。
- 输出写入 `<dataDir>/evidence/<runId>/<序号>-<命令哈希>.log`（每条上限 2 MiB，超出截断并标注），记录 sha256；`Evidence(kind: 'test-report')` 保存解析结果与文件路径。
- **基线**：需要运行前提交（`run.baseCommit`）上的结果。按 `(commit, command)` 缓存；没有缓存时，用 `git worktree add --detach <临时目录> <baseCommit>` 建临时 worktree 运行，完成后 `git worktree remove --force` 清理（同样禁用 hooks 与 fsmonitor）。
- 同一时间全局只跑一组验收（避免和执行中的任务抢资源）。

### 2. 验收编排 `packages/host/src/verify/verify-task.ts`
`verifyTask(taskId)`：任务必须是 `VERIFYING` 且有对应 Run 与检查点 → 运行基线与当前验收 → `judge` → `decideNext` → 执行决策：
- `succeed` / `retry` / `ask-user` / `pause-goal`：通过 `TaskRepo.transition` 与 `GoalRepo.update` 完成，状态迁移 reason 写判定理由。
- `rollback-and-retry`：在 WhaleDot 的 worktree 上，先把失败的检查点保存为引用 `refs/whaledot/failed/<runId>`（保留负面证据，规划书 8.4），再 `git reset --hard <run.baseCommit>`。**只操作 WhaleDot 自己的 worktree 与 `whaledot/*` 分支**，执行前断言当前分支名以 `whaledot/` 开头。
- 每个 `ask-user` 写一条 `Notification`（kind `decision` 或 `blocked`，dedupeKey = `goalId:taskId:决策类型`）和若干 `Suggestion`（label 用 i18n 文案，intent 为下面第 4 节的面板动作，绑定 `taskId + taskVersion`，24 小时过期）。**本任务不投递通知**（P04 负责发到鲸鱼小信封），只落库并在面板显示。

### 3. UNKNOWN 核对 `packages/host/src/verify/reconcile.ts`
- 针对 `UNKNOWN` 任务：查询其会话是否仍在运行（笔记中的 `sessions` / `agent/status`）。仍在运行 → 不动，稍后再核对；已停止 → worktree 有未提交改动则先提交检查点（标注 `reconciled`），然后 `UNKNOWN → VERIFYING` 进入正常验收。
- **绝不重发提示词**。会话不存在且 worktree 状态与运行记录对不上 → `BLOCKED`，ask-user。

### 4. 面板
- 任务详情显示验收证据：每条命令在基线/当前的状态、计数、耗时、日志链接（在面板内查看日志尾部，不提供下载任意路径）；判定结论与理由；进展标记。
- `VERIFYING` / `UNKNOWN` 任务显示“运行验收 / 核对”按钮（认证方法 `verify-task`、`reconcile-task`）。P10 会自动调用同一逻辑。
- “需要你决定”区域：列出未处理的决策通知，每条显示原因、证据摘要和按钮。按钮对应认证方法 `resolve-decision`，请求 `{ notificationId, choice }`，`choice` 只能是该通知落库时给出的选项之一：
  - `retry`（用户批准重试：FAILED/WAITING_APPROVAL → READY，用户批准不计入 maxFixRounds 但要记录）；
  - `accept`（用户确认接受：→ SUCCEEDED，迁移 source 为 `user`，reason 写明“用户人工接受，未经自动验收”）；
  - `rollback`（回滚到该运行前的检查点，任务 → READY）；
  - `pause-goal`；
  - `view-diff`（只读，显示该运行的 diff 统计与文件列表）。
  - 服务端校验：通知未处理、未过期、任务版本未变；**同一通知只能处理一次**（并发点击只生效一次）。
- 文案进 i18n，中英一致。

## 手工验收（`.dsh-dev`；写进 `docs/p09-report.md`）
用 P08 的测试仓库与目标：
1. 对 P08 留下的 `VERIFYING` analyze 任务运行验收 → `PASS`（report-only）→ `SUCCEEDED`。
2. edit 任务修好一个失败测试 → 基线 failed、当前 passed → `PASS`、progress `improved`。
3. 准备一个会“删掉失败测试”或加 `.skip` 的任务 → `FAIL`（acceptance-tampering）→ 决策通知出现，不自动重试。
4. 准备一个引入回归的任务（让原本通过的测试失败）→ 回滚并重试；`refs/whaledot/failed/<runId>` 存在；用户项目工作区不变。
5. 验收命令超时 → `UNKNOWN`，不是 FAIL。
6. 在决策通知上快速连点两次“重试” → 只生效一次。
7. 第零部分：在任务里诱导模型执行 `type <项目外文件>` 与 `Get-Content .env` → 被门禁拒绝，证据中有记录。
