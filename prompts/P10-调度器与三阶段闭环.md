# P10 Autopilot 调度器 + 三阶段闭环（M2 收官）

完成后，WhaleDot 应达到规划书的第一优先级：**用户只描述一次目标，就能看到一个真实项目在授权范围内持续、可靠地向前推进。**

## 第零部分：P09 审查遗留（先做，单独提交）

这三处在手动操作时不明显，但自动连续推进后会出问题：

1. **分析类任务被算作“无进展”**：`judge` 对 `report-only` 的分析任务返回 `progress: 'unchanged'`，`decideNext` 会把连续无进展计数加一。一个“分析 → 修复 → 分析”的正常计划可能因此被误判为停滞而暂停。
   - core：`progress` 新增 `'neutral'`。`report-only` 的分析/研究任务，以及基线已经全部通过且仍全部通过的 `doc` 任务，返回 `neutral`；`decideNext` 遇到 `neutral` 时计数保持不变（不加一也不清零）。更新测试与 `docs/core-domain.md`。
2. **验收已通过的任务会卡在“等你决定”**：`decideNext` 先判断停滞再判断 PASS，所以一个 PASS 的任务恰好达到停滞上限时，返回 `pause-goal`，`verify-task` 把它转到 `WAITING_APPROVAL`，而不是 `SUCCEEDED`。
   - 改为：任务本身 PASS 就 `SUCCEEDED`；停滞是**目标层面**的结论——目标转 `paused`，并生成一条绑定到目标（而非任务）的 `stalled` 决策通知。`Decision` 拆成 `taskOutcome` 与 `goalAction` 两部分；更新测试。
3. **验收结果“未知”会无限循环**：验收命令超时 → `UNKNOWN` → reconcile → `VERIFYING` → 再超时……自动推进下会反复执行整套测试。
   - 每个任务记录连续 `UNKNOWN` 验收次数；达到 2 次 → `WAITING_APPROVAL`，决策类型 `verification-unknown`（选项：重试验收 / 人工接受 / 暂停目标）。任何确定结论（PASS/FAIL 等）都把计数清零。测试覆盖这个循环。
4. 提交：`fix: neutral progress for reports, goal-level stall and bounded unknown verification`。

## 目标

实现调度器，让目标在用户开启“自主推进”后，**无需用户逐步操作**地连续执行：选任务 → 执行 → 验收 → 决定 → 选下一个任务，直到完成、需要用户决定、达到预算或停滞。对应规划书 F20、F23 的 MVP，验收用例 2、6、8、12。

## 设计约束

- **显式开启**：`ProjectGoal` 新增 `autopilot: { enabled: boolean, enabledAt?, disabledReason? }`，默认 `false`（包括已有目标，迁移时补默认值）。只有用户在面板点“开始自主推进”才开启。全局暂停、目标暂停、授权撤销、`autopilot.enabled = false` 任一成立 → 不启动新执行。
- **mode**：`suggest` 模式即使开启也不自动执行，只在有可执行任务时生成一条 `progress` 类通知“下一个任务已就绪”（等 P04 投递）；`autonomous` 与 `high` 在 MVP 中行为相同（`high` 不获得任何额外权限）。
- **后台执行**：用 P08 已查证的 `sessionController` 直连方式（`via: { kind: 'background' }`），不依赖任何浏览器身份。
- **调度器自身不做项目操作**（规划书 F20）：它只调用 P08 的 `executeNextTask`、P09 的 `verifyTask` / `reconcile`，以及下面的 planner。
- **不积压历史**：宿主重启后每个目标只补一次检查，不回放错过的触发。

## 第一部分：core（纯函数，带测试）

### 1. 调度决策 `packages/core/src/autopilot/tick.ts`
`planTick(snapshot) → TickAction`，输入为一个目标的只读快照（目标、有效授权是否存在、全局暂停、任务列表、进行中的运行、今日运行次数、全局并发占用、待处理决策数、planner 今日调用次数）。输出之一（按优先级）：
- `idle`（附原因：`global-paused` / `goal-paused` / `autopilot-off` / `no-scope` / `awaiting-decision` / `budget-exhausted` / `capacity-busy` / `run-in-progress`）；
- `reconcile(taskId)`：有 `UNKNOWN` 任务；
- `verify(taskId)`：有 `VERIFYING` 任务且没有对应的进行中运行；
- `execute`：有 `READY` 或可提升的 `PENDING` 任务（`suggest` 模式改为 `suggest-next`）；
- `plan`：所有任务都已终结（SUCCEEDED/CANCELLED）且目标未完成；
- `complete`：planner 上一轮明确判定目标完成，且最近一次验收全部通过。
- 有任何未处理的 `decision`/`blocked` 通知属于该目标 → `idle(awaiting-decision)`（不能绕过用户继续推进）。
- 今日运行次数达到 `limits.maxRunsPerDay`（按用户本地日期计）→ `idle(budget-exhausted)`。

### 2. Planner 契约 `packages/core/src/autopilot/planner.ts`
- `buildPlannerPrompt(goal, scopeSummary, history, locale)`：输入只包含结构化事实——目标、授权摘要、每个任务的标题/类型/最终状态/验收结论与理由、最近一次验收的计数、失败摘要。**不包含项目文件内容与模型的完成总结原文**（减少提示注入面）。要求模型只输出一个 JSON 代码块：`{ status: 'continue', tasks: [...] }`（1–3 个，按依赖顺序，依赖只能引用已有任务 id 或本批更早的任务）或 `{ status: 'complete', reason }` 或 `{ status: 'need-user', question }`。
- `parsePlannerResponse` → zod 校验；转换后经 `mergeProposedTasks` 合并。
- 规则：提议的 `edit`/`test`/`doc` 任务在授权为只读时一律拒绝；全部提议都被拒绝（重复/非法）视为一次“无进展”；planner 返回 `need-user` → 生成决策通知；每个目标每天最多 `plannerCallsPerDay`（默认 5，加入 limits）。
- planner **永远不能**修改授权、目标描述或验收命令。

## 第二部分：host

### 1. 调度器 `packages/host/src/autopilot/scheduler.ts`
- **触发器**（规划书 6.2）：
  - 事件：运行结束、验收完成、决策被处理、授权撤销、全局/目标暂停切换、自主推进开关变化 → 标记该目标为“待检查”；
  - 时间：每 60 秒巡检一次所有开启了自主推进的目标（只做检查，不代表一定执行）；
  - 启动：插件加载完成、存储可写后，先 `RunRegistry.recover()`，再对每个开启的目标做一次检查。
  - 同一目标的多个触发在 1 秒内合并为一次检查（去抖）。
- **执行**：每次检查构建快照 → `planTick` → 执行对应动作 → 动作完成后再标记一次“待检查”（形成连续推进）。
- **并发**：每个目标同一时间只处理一个动作（目标级互斥）；全局同时进行的模型运行数 `maxConcurrentRuns`（插件 Config，默认 1）；验收沿用 P09 的全局单批次。
- **planner 调用**：沿用 P07 的无工具模型调用方式（`dshDraftModel` 一类），超时 2 分钟；失败计入 planner 当日次数，不立即重试。
- **安全停机**：任何动作抛出未预期异常 → 该目标 `autopilot.enabled = false`，`disabledReason` 记录错误码，生成 `blocked` 通知；不影响其他目标。插件卸载时停止定时器、等待进行中的动作结束（最多 5 秒），不留后台任务。
- **追溯**：每个调度动作写一条 `StateTransition`-风格的调度日志（新表 `autopilot_events`：时间、目标、动作、原因、关联 task/run），用于报告与排查。

### 2. 目标完成
- `complete` → 目标状态 `completed`，`autopilot.enabled = false`，生成一条 `progress` 通知“目标已完成”，附最终检查点与验收结果摘要。**不自动合并到用户分支**（合并功能留待后续，届时必须用户确认）。

### 3. 追溯报告（验收用例 12）
- 认证方法 `export-trace`，请求 `{ goalId }`，返回 Markdown：目标与授权（含版本与撤销记录）→ 每个任务 → 每次运行（会话 id、时长、工具调用数、被拒次数）→ 证据（验收命令结果、diff 统计、日志文件 sha256）→ 检查点 → 决策与用户选择 → 调度事件。面板提供“导出追溯报告”按钮（浏览器下载为 `.md` 文件）。

### 4. 面板
- 目标详情顶部显示自主推进状态：`运行中 · 正在执行 <任务>` / `等待你决定` / `今日额度已用完（明天继续）` / `已暂停：<原因>` / `已完成`，以及最近 10 条调度事件。
- “开始自主推进 / 停止自主推进”按钮（认证方法 `set-autopilot`，开启时二次确认，确认框写明：将在 `<路径>` 内以 `<权限>` 自动执行，每天最多 `<N>` 次，可随时停止）。
- 文案进 i18n。

## 测试
- core：`planTick` 每个分支与优先级；planner 解析、只读授权下拒绝写类任务、`need-user`、每日上限。
- host：用假的 runner/verifier/planner 注入，模拟时间推进：
  - **三阶段依赖闭环**：analyze → edit → test 三个依赖任务，自动依次 SUCCEEDED，期间无任何用户操作（用例 2）；
  - 停滞：planner 连续提出无进展任务 → 达到 `maxStallRounds` 后目标暂停并有 `stalled` 通知，之后不再执行（用例 6）；
  - 有待处理决策时不推进；处理后恢复；
  - 预算：达到 `maxRunsPerDay` 后停止，跨日恢复；
  - 重启：运行中“重启”（重新构造调度器与存储）→ 任务 UNKNOWN → reconcile → 验收，期间提示词只发送过一次（用例 8）；
  - 触发合并：100 个事件只产生一次检查；
  - 授权撤销后不再执行；动作异常 → 该目标自动关闭自主推进。

## 手工验收（`.dsh-dev`；写进 `docs/p10-report.md`）
准备一个新的测试仓库：3 个失败测试，彼此独立或有简单依赖，`pnpm test` 为验收命令，`workspace-write`。
1. 新建目标（如“让全部测试通过，只做最小修复”）→ 开始自主推进 → **不做任何操作**，记录从开始到结束的时间线：任务、运行、验收结论、检查点。至少连续完成 3 个有依赖的任务阶段（用例 2）。期间鲸鱼应随会话活动（请用户目视确认，或如实写“未目视确认”）。
2. 用户项目的工作区与分支始终未变；`whaledot/*` 分支上有检查点提交。
3. 自主推进中途重启宿主 → 恢复后继续推进，没有重复发送提示词（对照会话历史）。
4. 一个无法完成的目标（例如测试依赖不存在的外部服务）→ 在有限轮次内停下并请求决定，而不是无限循环（用例 6）。
5. 导出追溯报告，检查能从目标一路追到每个运行的证据与检查点（用例 12）。
6. 全局暂停 → 正在进行的运行可以结束，但不再启动新运行；取消暂停后继续。
