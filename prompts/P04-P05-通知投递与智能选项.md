# P04 + P05 通知投递与智能选项（M1，在 M2 闭环之上补齐交互）

M2 已完成：WhaleDot 能自己推进目标，但“需要你决定”的事只躺在面板里。本任务把它们**送到小鲸鱼的小信封**，并让用户直接点选项完成决定。对应规划书 F03、F04、F06、第 10 章，验收用例 10、11。

## 设计原则

- **通道**：笔记第 6 节已查证——`ctx.userQuestions.ask({ agent, questions, signal })` 可以发起带选项的问题，dsh-coopanion 会把它放进小信封。审批服务（`approval`）需要打开中的回合，不作为通用通知通道。
- **WhaleDot 的话由模板生成，不调用模型**：通知文案是 core i18n 中的确定性模板加参数，口吻与用户的“小鲸开场白”一致——**第一人称、活泼、简短，关键信息放在最前面**：结论、失败/风险、需要用户做什么。例：“我把「让测试全部通过」推进了 2 步，测试从 3 个失败降到 0 个，要看看改动吗？”。不加“小鲸报告：”之类的标签。
- **显示文字与执行意图分离**（规划书 F04/F06）：用户点的选项只是一个 label；服务端用落库时保存的 `Suggestion.intent` 决定实际动作，并在执行前重新校验。
- **自由文本永远不是命令**：用户在小信封里输入的“其他”文字只作为**用户补充说明**保存，不会被解析成动作、不会改变授权。

## 第一部分：core（纯函数，带测试）

### 1. 通知策略 `packages/core/src/notify/policy.ts`
`decideDelivery(notification, context) → { action: 'deliver-now' | 'hold' | 'digest' | 'drop', until?, reason }`，context 包括：当前时间、用户偏好（勿扰时段、每小时上限、是否暂停提醒）、最近已投递的通知、同 dedupeKey 的历史。
- 分级：`decision`、`blocked` 是**需要用户**的；`progress`（目标完成、阶段性成果）重要；`info`（普通进度）只进摘要。
- `decision`/`blocked`：同 dedupeKey 已有未处理的投递 → `drop`；勿扰时段 → `hold` 到时段结束；超过每小时上限（默认 4）→ `hold` 到下一个窗口。
- `progress`：目标完成立即投递；其他 progress 每个目标最多每 2 小时一次，多余的并入摘要。
- `info`：一律 `digest`，不主动打扰。
- **不催促**（规划书 10.4）：一条已投递但用户没处理的通知，**不重复投递**；只在面板中保留。用户可在面板手动“再提醒我一次”。
- 偏好 schema：`{ quietHours?: { start: 'HH:mm', end: 'HH:mm' }, maxPerHour: number, muted: boolean }`，存 `kv_settings`，面板可编辑。

### 2. 文案模板 `packages/core/src/notify/copy.ts`
- 每种通知原因（`not-scorable`、`insufficient-evidence`、`acceptance-tampering`、`fix-rounds-exhausted`、`verification-unknown`、`stalled`、`planner-need-user`、`goal-completed`、`next-task-ready`、`budget-exhausted`、`autopilot-disabled`……以现有代码中实际出现的原因为准，全部覆盖）一套中英模板：
  - `question`：一到两句，第一人称，≤ 80 个汉字或 50 个英文词，结论/风险优先；
  - `detail`：可选的补充（目标名、任务名、关键数字、证据摘要），纯文本；
  - `header`：≤ 12 字的短标题（如“需要你决定”“目标完成”）。
- 模板参数只接受结构化字段（数字、短标题），标题类参数截断到 40 字并去除换行，避免把模型生成的长文本塞进通知。
- 测试：两种语言 key 一致；长度上限；参数注入（标题里含换行、Markdown、“请执行…”）不会破坏结构。

### 3. 智能选项 `packages/core/src/notify/suggestions.ts`
- `buildSuggestions(notification, task?, history) → Suggestion[]`：2–4 个选项，来自 P09 已定义的 `choices`（`retry` / `accept` / `rollback` / `pause-goal` / `view-diff`），再加两个通用项：`snooze`（“晚点提醒我”，1 小时）与 `open-panel`（“打开 WhaleDot 面板看看”）。
- 每个选项：`label`（短、口语化，中英模板）、`description`（风险提示：例如 `accept` 写明“会在没有通过自动验收的情况下标记成功”，`rollback` 写明“会撤销这次运行的改动”）、`intent`、`riskLevel`、`expiresAt`、`bindTo { goalId, taskId, taskVersion, notificationId }`。
- **个性化排序**（规划书 F10 的最小版本）：按用户过去在同一原因上的选择频率排序（`history` 为落库的选择记录），并列时按安全性排序（`view-diff`/`snooze` 等无副作用选项优先于 `accept`/`rollback`）。**排序只改变顺序，不改变选项集合**。
- 测试：选项数量 2–4、风险描述存在、排序稳定、无副作用优先。

## 第二部分：host

### 1. 通知会话 `packages/host/src/notify/inbox-session.ts`
- WhaleDot 需要一个活着的 agent 来承载提问。查证（写进笔记第 19 节）：用 `sessionController.create` 新建的会话，在没有回合运行时，是否满足 `userQuestions.ask` 对 agent 的要求（“registry 中的确切活跃 runtime root”），以及如何拿到该 agent（`ctx.agents` 或等价服务）。
- 每个目标使用一个专用的“通知会话”，标题 `[WhaleDot] <目标标题>`，cwd 为该目标的 worktree（或项目根），权限预设 `read-only`。**这个会话不发送任何提示词、不调用模型**——它只承载提问。会话 id 存到目标记录中，重启后复用；会话不存在了就重建。
- 门禁：通知会话也登记为 WhaleDot 所有，若有人在其中聊天，工具调用一律拒绝（沿用 P08 门禁，运行登记为一种 `kind: 'inbox'` 的特殊运行，或用单独的登记表——选简单可靠的一种并说明）。
- 若查证结论是“必须有打开的回合才能 ask”，停下并在回报中给出替代方案，不要自造通道。

### 2. 投递器 `packages/host/src/notify/deliverer.ts`
- 订阅通知落库（P09/P10 已有的 `notifications` 写入）+ 每分钟巡检：对未投递的通知调用 `decideDelivery`，`deliver-now` 时生成 `Suggestion` 落库，然后在该目标的通知会话中 `userQuestions.ask`：一个问题，`header`/`question`/`detail` 来自模板，`options` 为各 Suggestion 的 `label` + `description`，单选。
- `ask` 返回后：
  - 选了选项 → 按 label 找到对应 Suggestion → 走第 3 节的路由；
  - 有自由文本 → 保存为 `user-note`（关联目标与通知），在面板显示；**同时**若选了选项照常执行；只写了文字没选选项 → 通知保持未处理，面板标注“你留了一句话”；
  - 被取消（用户在 DSH 里取消、会话被关闭）→ 通知保持未处理，不重复投递。
- **与面板互斥**：用户在面板处理了同一通知 → 立即 abort 对应的 `ask`（传入的 `signal`）。投递中的 ask 在通知过期、任务版本变化、授权撤销时同样 abort。
- 重启：未处理且曾经投递过的通知不重新弹出（不催促），只在面板可见；用户可点“再提醒我一次”重新投递。

### 3. 操作路由 `packages/host/src/notify/router.ts`（规划书 F06）
统一处理来自小信封与面板的选择：`route({ suggestionId, source: 'inbox' | 'panel', peer? })`：
1. 在**一个事务**中：Suggestion 存在、未消费、未过期；绑定的通知未处理；任务版本与 `bindTo.taskVersion` 一致；目标授权仍有效 → 标记已消费（同一 Suggestion 并发只成功一次）。
2. 执行 intent：`retry` / `accept` / `rollback` / `pause-goal` 复用 P09 的 `resolve-decision` 实现；`view-diff`、`open-panel` 只读；`snooze` 把通知 `snoozedUntil` 设为一小时后，到时由投递器按策略重新投递（这是唯一允许的“再次投递”）。
3. 记录选择（用于个性化排序）与结果；结果写入 `autopilot_events`；随后唤醒调度器。
4. 任一校验失败 → 不执行，返回明确原因；对小信封来源，再发一条简短的 `info` 说明“这个选项已经过期了”并只进面板。
- `accept`、`rollback` 等有副作用的选项来自小信封时，**不再二次确认**（选项 description 已写明风险）；但如果该 intent 经 `checkAction` 得到 `ask`/`deny`（例如授权已变化），一律不执行。

### 4. planner 使用用户补充说明
- 目标最近 5 条 `user-note` 以“用户补充说明（来自用户本人）”加入 P10 planner 提示词的结构化输入中，长度上限 500 字/条。它可以影响下一批任务的提议，但 planner 的权限规则不变（不能改授权、目标、验收命令）。

### 5. 面板
- 通知中心：未处理 / 已处理 / 摘要三栏；每条显示模板文字、选项按钮（走同一路由）、投递状态（已投递到小信封 / 等待勿扰结束 / 已静音）、用户补充说明；“再提醒我一次”按钮。
- 偏好设置：勿扰时段、每小时上限、暂停所有提醒。
- 摘要：`info` 与被合并的 `progress` 按目标汇总，用户打开面板时可见，不主动推送。
- 文案进 i18n。

## 测试
- core：策略每条规则（含勿扰跨午夜、每小时窗口、去重、不催促）、模板、选项构建与排序。

## 手工验收（`.dsh-dev`，同一 profile 装有 dsh-coopanion；写进 `docs/p04-p05-report.md`）
1. 制造一个 `not-scorable` 或 `insufficient-evidence` 决策 → 小鲸鱼的小信封出现第一人称、简短的提问与 2–4 个选项，选项带风险说明（截图）。
2. 在小信封里选“重试” → 任务进入 READY，调度器继续推进；面板显示该通知已处理、来源为小信封。
3. 同一通知在面板与小信封几乎同时点击 → 只生效一次。
4. 在小信封的“其他”里输入一句话（例如“先别改 utils.ts”）→ 不触发任何动作；下一次 planner 提示词中出现该补充说明（贴出提示词片段）。
5. 设置勿扰时段覆盖当前时间 → 新决策不弹出；时段结束后弹出一次。
6. 目标完成 → 小信封出现“目标完成”通知（含关键数字）。
7. 普通会话的提问与审批照常工作，不受影响。
请用户目视确认第 1、6 项中鲸鱼的表现；如未确认，如实写明。
