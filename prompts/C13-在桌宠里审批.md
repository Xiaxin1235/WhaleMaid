## 背景

现在桌宠的信封里能直接回答普通单选提问，见 `src/inbox-questions.ts`。审批却仍然要切回 Harness 处理，`docs/usage.md` 里写的是“审批、多选和计划审阅仍在 Harness 处理”。WhaleMaid 高权限模式下的危险操作审批、以后对话里调用 Codex 的审批，都需要用户切回 Harness，打断工作。

用户要求：**审批也能在桌宠里直接回答**，不用切回 Harness。

## 先查证（写进报告，附 rc.3 类型定义出处）

1. `@deepseek-ai/dsh-user-approval` 的 `ApprovalService.request` 通过 `ctx.waterfall(..., 'approval/request', req, fallback)` 调用回答者链。
   - 桌宠能否像 `InboxQuestions.track` 处理提问那样，作为**第二个回答面**加入这条链？
   - 也就是：给后续回答者一个派生的中止信号，与 Harness 自己的界面竞争，先答者生效；桌宠答了，Harness 那边的提示随之撤回；Harness 先答了，桌宠这边随之撤回。
2. `ApprovalRequest` 的字段标为 `readonly`。
   - 每次 waterfall 传进来的是新的事件信封，还是调用方的原对象？
   - 能否安全替换 `signal`？
   - 若不能，找出不修改请求、也能让下游撤回的公开做法；找不到就停下说明，**不要**用私有字段或猴子补丁。
3. `ApprovalOutcome` 有哪些取值？桌宠只允许产生“允许一次”和“拒绝”这两种。
4. `approval/asked` 事件里的 `reason` / `displayReason`、`toolName`、`callId`，哪些可以用来给用户展示“要批准的是什么”？WhaleMaid P14I 已把可读文字放进 `reason`。

## 实现

### 宿主端

- 新增一个与 `InboxQuestions` 对称的审批回答模块：
  - 只登记**仍在等待**的审批；
  - 会话结束、请求被撤回或 Harness 先答时，立即移除。
- 下发给桌宠的内容只包括：
  - 审批 ID、会话 ID、会话名；
  - 工具名；
  - 可读原因：截断到 600 字，去掉控制字符；
  - 创建时间。
  
  **不下发**工具的完整参数。
- 桌宠回答走现有已校验的 IPC 和 Host 通道，与聊天、提问回执的校验方式一致：
  - 校验来自本窗口主 frame；
  - 审批 ID 精确匹配且仍在等待；
  - 答案只能是 `allow-once` 或 `reject`。
  
  过期、重复或不匹配的回答一律拒绝，并返回明确的失败码。
- **不提供**“总是允许”“本会话都允许”之类的选项，不修改会话的审批策略。

### 桌宠界面（两种界面风格都要做）

- 待审批事项出现在信封里，标记为“需要批准”，信封计数包含审批。
- 打开后显示：
  - 来自哪个会话；
  - 要做什么，即可读原因；
  - “允许一次”和“拒绝”两个按钮，以及“去 Harness 查看”入口（打开源会话）。
- **防误触**：
  - “允许一次”不是默认焦点，按回车不会触发允许；
  - 面板打开后 1 秒内允许按钮不可点；
  - 拒绝可以立即点。
- 回答后显示“已允许”或“已拒绝”，然后移出信封。Harness 先答了的，显示“已在 Harness 处理”后移出。
- **安静模式**：照常只亮信封、不弹框。普通模式：新的审批像提问一样弹出提醒。
- 设置里加开关“在桌宠里回答审批”，**默认开启**，中英文案。关闭后，审批只计入信封并提示去 Harness，桌宠不加入回答者链。
- 菜单、托盘不提供审批按钮。

### 文档

`docs/usage.md` 和 `docs/session-chat-contract.md` 说明：

- 审批可以在桌宠里回答；
- 只有“允许一次 / 拒绝”；
- 与 Harness 竞争时先答者生效；
- 防误触规则；
- 开关的作用。
