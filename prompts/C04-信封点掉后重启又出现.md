# C04 鲸鱼插件：信封条目点掉后，重启 Harness 又出现

**前置**：C03 已提交（`399ad8f`），工作区干净。用户日常 profile 已通过 `link:` 使用本仓库 `whaledot-local` 分支的构建产物——**修改期间不要重新构建到 `dist/` 之外的位置，也不要在日常 profile 上测试**；完成并提交后再统一 `npm run build`，由用户重启 Harness 生效。

## 用户报告
在日常 DSH 中把小信封里的条目点掉（查看/去处理/关闭）后，**每次重新打开 Harness，这些条目都会重新出现**。

## 已知代码事实（核对源码）
- 渲染页的“已读/已查看”集合（如 `web/pet.js` 的 `acknowledgedResults`、`shownResults`）只在内存中。
- `docs/usage.md` 写明：通用异常/暂停项点击“去处理”后清除该轮条目，但“查看回执只在当前桌宠窗口运行期有效”。
- `src/notification-broker.ts` 的 `restore()`：重启时从会话恢复条目；注释写明“Restored requests keep their entrance”（未处理的提问/审批保留入口）。
- 新回复在重启后不会重新标为未读（已有设计）。

## 第一部分：复现与归类（先做，写进报告）
在 WhaleDot 隔离测试环境中（`scripts/dev-host.ps1`，独立的测试鲸鱼数据目录）分别制造并点掉：① 回复；② 以错误结束的回合（异常）；③ 暂停/被阻止的回合；④ 模型发起但未回答、已超时（`continued`）的提问；⑤ 仍在等待的提问；⑥ 审批。重启测试宿主后，记录哪些重新出现。

## 第二部分：修复

1. **持久化用户的“处理过”记录**：在 Electron userData 下新增一个小型存储（参照 `src/companion-store.ts` 的写法与校验方式，或放进现有的 companion 存储中），保存用户已经查看/关闭过的条目键：
   - 键必须稳定且能区分不同事件：至少包含 `sessionId` + 条目类型 + 回合号/序号（或 callId）。同一会话之后出现**新的**异常或新提问，必须照常出现。
   - 上限 1000 条，超过 30 天的自动清理；写入用原子写，损坏时丢弃并从空开始（只会导致条目重新出现，不会丢数据）。
2. **重启时的规则**：
   - 异常、暂停条目：用户点掉过 → 重启后不再出现。
   - 已超时（`continued`）且用户点掉过的提问：重启后不再出现（它在 Harness 会话中仍可查看与回答）。
   - **仍在等待回答的提问与审批**：保持现状，重启后仍然保留入口——它们确实还没处理，隐藏会让工具调用一直卡住。但若用户点了“稍后”，沿用现有的稍后逻辑。
   - 回复：保持现有行为。
3. 新增设置项不需要；这是默认行为修正。若 `docs/usage.md` 与 `docs/notification-contract.md` 中有“只在当前运行期有效”的描述，更新为新行为。
4. 测试：存储的读写、上限与过期、损坏恢复；`restore()` 对每类条目的重启行为（含“同一会话的新异常仍会出现”）；`npm test`、`npm run test:inbox-ui` 通过；涉及原生窗口则跑 `npm run test:desktop`。
